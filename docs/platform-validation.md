# Datadog platform validation

The default Molecule matrix exercises Linux Agent 7 installation, service startup, idempotence, and Debian legacy repository migration. It does not validate Windows, macOS, SUSE, or single-step instrumentation (SSI). The following are external validation procedures, not claims that these configurations have passed. Use disposable hosts and a Datadog test account; the installer and agent contact Datadog and may incur charges. Record the OS and architecture, Ansible and role versions, Agent version, playbook variables, first and second run results, and cleanup for each run. Keep API keys and installer credentials out of logs and artifacts.

- **SUSE:** On a supported SLES or openSUSE host with systemd and repository access, run the role with Agent 7 enabled and a test API key. Verify the installed package, configured Datadog zypper repository and signing keys, and running service; run it again and check idempotence. Repeat with a supported pinned Agent version and verify the installed version.
- **Windows:** On a supported Windows host configured for Ansible with `ansible.windows` installed, install Agent 7 with a test key and verify the installed version, configuration and running Datadog service. Run again for idempotence. Separately test a pinned version, `datadog_windows_skip_install`, and a controlled remote update in progress; verify the latter skips installation and restart without losing configuration.
- **macOS:** On supported Intel and Apple silicon hosts with Ansible connectivity, install Agent 7 with a test key. Verify the architecture-specific package, version, generated configuration and running agent. Run again for idempotence, then repeat with a supported pinned version.
- **SSI:** On a supported disposable Linux host, set `datadog_apm_instrumentation_enabled: host` and a test API key. Verify the installer completes, instrumentation is installed, and `install-ssi.sh` is removed from `datadog_ssi_script_dir`; run again and record any changes. Test a supported instrumented application and confirm traces arrive in the test account. Separately check `docker` or `all` with Docker present, and check that an invalid or empty value fails. Test a custom installer registry and authentication only with a controlled registry and secret-safe logging.

Do not run these procedures against production hosts. Preserve the results and exact failures with the change under review; syntax and lint checks cannot establish platform or installer behavior.
